## 第一部分：专业术语与歧义问题

### 🔴 严重问题

#### 1. **"翻卡"术语未定义**
**位置**：第四章第二阶段（辩论时）第172行
```
禁止主动翻卡自证，允许谎报身份
```

**问题分析**：
- "翻卡"是典型的跑团俚语，在正式规则中未经定义就使用
- 与第一章"身份公开（暴露）"概念的关系不明确
- "主动翻卡"与"治安阵营施放技能后被强制公开身份"的机制冲突

**形式化建议**：
```
定义 1.3 【身份公开机制】
  公开方式 ::= 被动公开 | 主动声明
  
  被动公开：当且仅当以下条件触发时，GM 向全场展示玩家的真实角色卡
    - 治安阵营角色施放主动技能（圣杀者/圣骑士/大法师）
    - [其他强制公开条件，如果有的话]
  
  主动声明：玩家在辩论时阶段可以口头宣称自己的身份，但该声明不受规则约束（可以撒谎）
  
  约束：玩家不得主动要求 GM 展示其真实角色卡以自证身份（禁止"主动翻卡"）
```

#### 2. **"存活玩家总数"的定义域模糊**
**位置**：第二章 2.2 邪恶阵营胜利条件（第53行）
```
场上存活的【嗜血者】数量 ≥ 存活玩家总数的 50%
```

**问题分析**：
- "存活玩家总数"是否包含被大法师复活的玩家？（应该包含，但未明确）
- 是否包含刚刚被投票处决但尚未结算的玩家？（时序问题）
- 边界条件：3 人场时，1 嗜血者 + 2 非嗜血者，1/3 ≈ 33.3% < 50%，不满足；但文档 Q4 中的案例 "1 嗜血者、1 非常者、1 异星客" 暗示嗜血者占比为 1/3，却触发了混沌优先级判定，说明邪恶阵营条件被检查了

**形式化建议**：
```
定义 2.1 【存活玩家集合】
  设游戏中所有玩家的集合为 P = {p₁, p₂, ..., pₙ}
  
  存活玩家集合 Alive(t) ⊆ P，在时刻 t 时定义为：
    Alive(t) = { p ∈ P | p 未被处决 ∨ (p 曾被复活且未再次被处决) }
  
  胜利检定时刻 t_check：每轮猎杀时结束后，所有结算完成时
  
  邪恶阵营胜利条件：
    ∃ t_check : |Bloodthirsty ∩ Alive(t_check)| / |Alive(t_check)| ≥ 0.5
    其中 Bloodthirsty = { p ∈ P | role(p) = 嗜血者 }
```

#### 3. **"潜伏者"与角色卡不对应**
**位置**：第二章 2.2 邪恶阵营（第52行）
```
阵营构成：由潜伏者与嗜血怪物组成。
```

**问题分析**：
- 第三章只定义了【嗜血者】和【非常者】，没有"潜伏者"和"嗜血怪物"
- 疑似"潜伏者"指【非常者】，"嗜血怪物"指【嗜血者】，但用词不统一

**修复方案**：
```
统一术语：
  邪恶阵营 = { 嗜血者, 非常者 }
  
  嗜血者 := 具有夜间猎杀能力的邪恶角色
  非常者 := 不具备猎杀能力的邪恶人类伪装者
```

#### 4. **"席位靠前"未定义**
**位置**：第三章 3.2 嗜血者技能（第94行）
```
若意见无法统一，则由席位靠前的嗜血者决定
```

**问题分析**：
- 未定义"席位"是游戏开始时的初始编号、发言顺序、还是其他排序规则
- 如果席位是动态的（如按发言顺序），则可能引发歧义

**形式化建议**：
```
定义 1.4 【玩家席位编号】
  在游戏初始化时，GM 为每个玩家分配唯一的自然数编号 seat_id ∈ [1, n]
  seat_id 在整局游戏中不变（即使玩家阵亡或复活）
  
  席位靠前 := seat_id 较小的玩家优先
```

## 第二部分：逻辑漏洞与边界情况

### 🔴 严重漏洞

#### 漏洞 1：**平票决选机制下的无限循环风险**
**位置**：第四章第三阶段（投票时）第176-179行

**漏洞描述**：
```
场景：6 人存活，初次投票 A、B 各得 3 票
触发决选：【全部处决】vs【全部赦免】
若决选再次 3:3 平票 → 默认全部赦免

但这里存在逻辑漏洞：
1. 如果玩家恶意利用平票规则，可以永久拖延游戏（一直投平票）
2. 规则未约束"全部赦免"后的下一步操作（直接进入裁判时？还是重新发起投票？）
```

**形式化修复**：
```
投票时状态机：

State 1: 初次投票
  → 若存在唯一最高票者 → 处决该玩家 → 进入裁判时
  → 若存在 k≥2 个最高票者且票数相同 → 进入 State 2

State 2: 决选投票（二选一）
  选项 A：处决所有最高票者
  选项 B：赦免所有最高票者
  
  → 若 |Vote(A)| > |Vote(B)| → 处决所有最高票者 → 进入裁判时
  → 若 |Vote(B)| > |Vote(A)| → 赦免 → 进入裁判时
  → 若 |Vote(A)| = |Vote(B)| → 强制赦免 → 进入裁判时
  
约束：每轮投票时最多进行 2 次表决（初次 + 决选），决选结果强制生效，禁止再次投票
```

#### 漏洞 2：**大法师复活时序漏洞**
**位置**：第三章 3.3 大法师技能（第110-113行）

**漏洞描述**：
```
问题 1：大法师在裁判时复活一名玩家，该玩家是否获得"本轮裁判时"的行动权？
  - 如果复活的是圣杀者，TA 能否在本轮裁判时立即使用技能？
  - 如果复活的是嗜血者，TA 能否参与本轮猎杀时的投票？

问题 2：复活顺序问题
  - 若大法师复活了圣骑士，圣骑士能否在本轮裁判时立即守护？
  - 规则第四章第183-186行规定了裁判时的执行次序（圣杀者→圣骑士→大法师）
  - 这意味着大法师是最后行动的，复活的圣骑士/圣杀者已经错过本轮行动窗口
  - 但规则未明确说明

问题 3：冷却时间的"轮"定义
  - "每 2 轮仅可使用 1 次"：是指两个完整轮次之间，还是间隔一轮？
  - 例：第 1 轮使用，第 2 轮冷却，第 3 轮可用？还是第 4 轮可用？
```

**形式化修复**：
```
定义 3.1 【大法师复活机制】

冷却时间：
  设大法师上次使用技能的轮次为 round_last
  当前轮次为 round_current
  可使用条件：round_current - round_last ≥ 2
  
复活时序：
  1. 大法师在裁判时宣告复活目标 p
  2. GM 立即公开大法师身份
  3. 玩家 p 的状态变更为 Alive(t)，恢复所有技能与权利
  4. 玩家 p 在本轮裁判时的行动窗口已关闭，无法施放技能
  5. 玩家 p 从下一阶段（猎杀时或下一轮信息时）开始完全生效
  
特殊约束：
  若复活目标为嗜血者，TA 可以参与本轮猎杀时的投票
  若复活目标为治安角色，TA 需等到下一轮裁判时才能施放技能
```

#### 漏洞 3：**圣骑士守护的"下一轮裁判时"定义模糊**
**位置**：第三章 3.3 圣骑士技能（第121行）

**漏洞描述**：
```
"该目标在下一轮【裁判时】到来前，免疫所有形式的处决"

时序歧义：
  场景：第 N 轮裁判时，圣骑士守护玩家 A
  
  问题：A 的免疫持续时间是？
    解释 1：从第 N 轮猎杀时开始，到第 N+1 轮裁判时开始前
            （即保护 A 免受第 N 轮猎杀 + 第 N+1 轮投票处决）
    
    解释 2：从第 N 轮裁判时结束后，到第 N+1 轮裁判时结束前
            （更长的保护期，可能不合理）
    
  边界问题：如果 A 在第 N 轮投票时已经被投票处决，圣骑士还能守护吗？
```

**形式化修复**：
```
定义 3.2 【圣骑士守护时效】

设圣骑士在第 k 轮裁判时对玩家 p 施放守护，守护效果的时间窗口为：
  
  T_protect(p, k) = [Phase(k, 裁判时_end), Phase(k+1, 裁判时_start))
  
  即从第 k 轮裁判时结束后，到第 k+1 轮裁判时开始前
  
保护内容：
  在 T_protect 期间，玩家 p 免疫以下伤害：
    - 第 k 轮猎杀时的秘密处决
    - 第 k+1 轮投票时的公共处决
    - 第 k+1 轮裁判时的圣杀者铁腕神裁（根据 FAQ Q2）
  
前置条件：
  施放守护时，玩家 p 必须处于存活状态
  若 p 在第 k 轮投票时已被处决，守护无效（技能施放失败）
```

#### 漏洞 4：**验尸官的"历史上被处决"定义不完整**
**位置**：第三章 3.1 验尸官技能（第84行）

**问题分析**：
```
"指定一名历史上被处决（含公共处决与秘密处决）的阵亡玩家"

缺失定义：
1. "历史上"是指游戏开始以来，还是验尸官获得技能以来？（应该是前者，但未明确）
2. 如果验尸官在第 1 轮获取信息，此时无人阵亡，技能是否可以跳过？
3. 验尸官能否查验自己（如果被复活后）？
```

**形式化修复**：
```
定义 3.3 【验尸官技能作用域】

设游戏开始时刻为 t₀，当前时刻为 t
验尸官可查验的玩家集合 V(t) 定义为：

V(t) = { p ∈ P | ∃ t' ∈ [t₀, t) : p 在 t' 被处决 ∧ p ∉ Verified }

其中：
  - Verified 为验尸官已查验过的玩家集合（不可重复查验）
  - "被处决"包含公共处决与秘密处决
  - 若 p 被大法师复活后再次阵亡，p 只能被查验一次（按首次阵亡计）

特殊情况：
  - 若 V(t) = ∅（无可查验目标），验尸官本轮信息时技能自动跳过
  - 验尸官不能查验自身（即使被复活）
```

#### 漏洞 5：**非常者的"单向隐藏"机制不完整**
**位置**：第三章 3.2 非常者特性（第99行）

**问题分析**：
```
"不参与嗜血者的夜间猎杀频道，不掌握嗜血者队友身份（单向隐藏）"

逻辑矛盾：
1. 嗜血者是否知道非常者的存在？（规则未说明）
2. 如果嗜血者不知道非常者，当非常者被投票处决时，嗜血者可能误以为减少了一个敌人
3. 如果嗜血者知道非常者，那"单向隐藏"不成立

边界问题：
  场景：6 人局，2 嗜血者 + 1 非常者 + 3 平凡
  投票处决了非常者后，场上剩 5 人，嗜血者占 2/5 = 40% < 50%
  但嗜血者不知道非常者已死，可能误判胜利条件
```

**形式化修复**：
```
定义 3.4 【邪恶阵营信息不对称】

信息可见性矩阵：
  设邪恶阵营玩家集合 E = {嗜血者₁, 嗜血者₂, ..., 非常者}
  
  游戏开始时的信息分发：
    - 每个嗜血者知道所有其他嗜血者的身份（互知）
    - 每个嗜血者知道邪恶阵营的总人数 |E|，但不知道非常者的具体身份
    - 非常者不知道任何邪恶阵营成员的身份（完全单向）
  
  推理约束：
    - 嗜血者可以通过 |E| 和已知嗜血者数量推断非常者数量
    - 嗜血者无法直接识别非常者的具体身份
```

## 第三部分：形式化缺陷

### 🔴 缺少的核心定义

#### 1. **游戏初始化配置规则**
**缺失内容**：
- 不同玩家数量下，各阵营的角色配置比例
- 例：8 人局应该有几个嗜血者？几个治安角色？
- 是否允许重复角色？（如 2 个吹哨人）

**建议补充**：
```
定义 0.1 【游戏配置规范】

设玩家总数为 n，角色配置函数 Config(n) 返回合法的角色列表

约束条件：
  1. 每个角色最多出现 1 次（无重复角色）
  2. 嗜血者数量 ∈ [⌈n/5⌉, ⌊n/3⌋]（防止过强或过弱）
  3. 治安角色总数 ≤ ⌊n/4⌋
  4. 混沌角色总数 ≤ 2
  5. 平凡阵营占比 ≥ 40%

推荐配置表：
  n=6: 1嗜血+1非常+1吹哨+1验尸+1普通+1痴呆
  n=8: 2嗜血+1非常+1圣骑+1吹哨+1验尸+1异星+1普通
  n=10: 2嗜血+1非常+1圣骑+1大法师+1吹哨+1验尸+1异星+1普通+1痴呆
```

#### 2. **胜利检定的精确时刻定义**
**缺失内容**：
- 胜利检定在"每轮结束时"执行，但未明确是在猎杀时结算后，还是阵亡者出局后

**建议补充**：
```
定义 4.1 【胜利检定时序】

每轮游戏循环的最后一步，在猎杀时完成后，执行以下步骤：

Step 1: 结算猎杀伤害，更新 Alive(t)
Step 2: GM 宣告本轮死亡结果
Step 3: 执行胜利检定 Victory_Check(t)
Step 4: 若有阵营获胜，游戏终止；否则进入下一轮信息时

Victory_Check(t) 的执行顺序（短路求值）：
  1. 检查混沌阵营条件：|Alive(t)| ≤ 3 ∧ ∃ p ∈ Chaos : p ∈ Alive(t)
     → 若成立，混沌阵营获胜，游戏终止
  
  2. 检查邪恶阵营条件：|Bloodthirsty ∩ Alive(t)| / |Alive(t)| ≥ 0.5
     → 若成立，邪恶阵营获胜，游戏终止
  
  3. 检查治安阵营条件：(Evil ∪ Chaos) ∩ Alive(t) = ∅
     → 若成立，治安阵营获胜，游戏终止
  
  4. 检查平凡阵营条件：(Evil ∪ Chaos ∪ Law) ∩ Alive(t) = ∅
     → 若成立，平凡阵营获胜，游戏终止
  
  5. 若以上条件均不满足，游戏继续
```

#### 3. **随机性来源的形式化定义**
**缺失内容**：
- 吹哨人的"随机指定"机制未明确随机源
- 痴呆者的"掷骰或抽签"未规定具体实现

**建议补充**：
```
定义 1.5 【随机机制规范】

游戏中的随机事件必须由 GM 使用密码学安全的随机数生成器（CSPRNG）或物理骰子执行

1. 吹哨人随机目标：
   候选集合 = Alive(t) \ {吹哨人自己}

   候选集合 = Alive(t)（包含自己）

3. 角色分配：
   GM 将所有角色卡洗混后，随机分配给玩家（确保无人事先知晓他人角色）
```

## 第四部分：形式化改进计划

### 阶段 1：建立形式化语言基础（优先级 P0）

#### 1.1 定义核心数据结构
```rust
// 玩家状态
enum PlayerState {
    Alive,
    Dead,
}

// 角色定义
enum Role {
    // 平凡阵营
    Commoner,
    Whistleblower,
    Coroner,
    
    // 邪恶阵营
    Bloodthirsty,
    Abnormal,
    
    // 治安阵营
    Archmage,
    Paladin,
    Executioner,
    
    // 混沌阵营
    Demented,
    Alien,
}

// 种族标签
enum Species {
    Human,
    NonHuman,
    SuperHuman,
}

// 阵营
enum Faction {
    Commoner,
    Evil,
    Law,
    Chaos,
}

// 玩家数据
struct Player {
    id: PlayerId,
    seat_id: u8,
    role: Role,
    species: Species,
    faction: Faction,
    state: PlayerState,
    is_revealed: bool,
}
```

#### 1.2 定义游戏状态机
```
GameState ::= {
    players: Vec<Player>,
    round: u32,
    phase: Phase,
    history: EventLog,
}

Phase ::= 
    | InformationPhase
    | DebatePhase
    | VotingPhase { stage: VotingStage }
    | AdjudicationPhase
    | HuntPhase

VotingStage ::= 
    | FirstVote
    | TieBreaker { candidates: Vec<PlayerId> }
```

### 阶段 2：建立约束验证系统（优先级 P1）

#### 2.1 不变式（Invariants）
```
全局不变式：
  INV1: ∀ p ∈ Players : role(p) 在整局游戏中不变（除非被复活）
  INV2: ∀ p ∈ Players : seat_id(p) 在整局游戏中不变
  INV3: |Players| 在游戏开始后不变（不增加玩家）
  INV4: 每轮必须按顺序执行 5 个阶段，不可跳过或重复

阶段不变式：
  INV_Vote: 投票时，每个存活玩家恰好投出 1 票
  INV_Hunt: 猎杀时，嗜血者最多处决 1 名玩家
  INV_Resurrect: 大法师每 2 轮最多复活 1 名玩家
```

#### 2.2 前置条件（Preconditions）
```
技能施放前置条件：
  PRE_Whistle: 吹哨人存活 ∧ |Alive| ≥ 2
  PRE_Coroner: 验尸官存活 ∧ ∃ p : p 已阵亡且未被查验
```
